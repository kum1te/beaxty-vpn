# Проверка BeaxtyVPN — 26 сентября 2026

Проверен commit `bc06d89` (`main`, `origin/main`). На момент начала проверки `docs/` не отслеживался Git. Исходный аудит не менял сетевые настройки ОС; перечисленные ниже исправления были внесены после проверки в `dev` и отдельно проверены.

После первой волны исправлений в `dev` были закрыты локальные дефекты: HWID больше не отправляется сырым machine-id, URL-фильтр блокирует RFC1918/ULA и dotted localhost, встроенный кабинет корректно разбирает userinfo и отклоняет HTTP-auth dialogs, `--tray` зарегистрирован и скрывает окно, ссылки подписок маскируются в логах, а privileged dashboard RPC ограничен путями, переданными при запуске. Первоначально SUID-ядро ещё оставалось; ниже приведён его статус после следующего исправления.

**Вывод:** текущую сборку нельзя считать готовой к релизу с обещанием защиты данных и надёжного Kill Switch. Есть критическая проблема границы привилегий, воспроизведённая утечка исходного идентификатора устройства и несколько ошибок защитных механизмов. Открытие исходников и выпуск стабильного приложения — разные этапы: перед первым необходимо проверить историю и реальные учётные данные, перед вторым — закрыть дефекты ниже.

**Объём и ограничения**

**Статус последующей работы в `dev`:** старый `setup-cap.sh` удалён; bridge больше не выдаёт ядру SUID-root; Linux-настройка TUN копирует проверенный по SHA-256 core в root-owned `/usr/lib/beaxty-vpn/<UID>`, ограничивает проход к нему POSIX ACL только текущим UID и назначает только `CAP_NET_ADMIN` отдельным узким помощником за один вызов Polkit, без shell. Помощник повторно проверяет UID из `PKEXEC_UID`, digest и расположение встроенного ядра; копирует без следования по симлинкам и перезаписи существующего целевого файла. Сборка, Linux-пакет и проверка зависимостей помощника прошли; реальный Polkit-диалог для новой версии не запускался, туннель во время этой проверки не запускался. При старте приложение выбирает такую копию только при совпадении digest, владельца, mode bits, ACL и точной file capability. Kill Switch по-прежнему не является системным firewall: интерфейс и статус теперь явно предупреждают, что после падения core трафик может идти напрямую. Подключение очищает намерение пользователя при раннем отказе, сообщает о падении ядра и больше не удаляет QLocalSocket после передачи владения IPC-клиенту; проверку состояния сокета заменил атомарный флаг с поколением соединения. Запросы Start/Stop теперь идут через отдельную последовательную очередь, `cleanup()` очищает очередь и дожидается выполняющихся задач, а незавершённая операция Polkit отменяется при выходе. Флаги traffic looper стали атомарными. Для этих изменений ещё нужны ThreadSanitizer и стресс-тесты быстрого connect/disconnect/restart; построение конфигурации в фоне по-прежнему читает общие репозитории. Сохранённая тема/настройки загружаются после открытия БД; UI-тест проверяет обновление переключателей без запуска core. Linux-сборка содержит Noto Color Emoji с OFL notice.

Повторная Linux-упаковка прошла статическую проверку AppDir: ноль отсутствующих ELF-зависимостей и ноль утечек Qt из системы; AppImage 244 MiB, portable tarball 263 MiB. В актуальном deployment log ошибка `Missing qml module: QtQuickControls2` не повторилась. Сам AppImage здесь не запускался: это поднимет упакованный Throne core, а реальное TUN-поведение запрещено условиями аудита. Поэтому headless GitHub Actions smoke test и runtime импорт QML внутри AppImage остаются непроверенными.

Изучены карта проекта, CMake, release workflow, основной C++/QML слой, запуск и остановка ядра, IPC/проверка родителя, сетевой helper, импорт подписок, генератор маршрутизации, хранение, диагностический отчёт и существующие тесты. При спорном выводе по IPv6 дополнительно изучен установленный исходник sing-tun v0.9.0-beta.4.

Это углублённое ревью основных путей исполнения с локальными проверками. Оно не является построчной сертификацией всех сторонних библиотек. Реальный VPN-трафик, обрыв туннеля, Windows/macOS, веб-страница кабинета и эксплуатация от root не испытывались. Рабочие подписки сервиса не запрашивались.

**Приоритеты:** P0 — устранить до безопасного распространения; P1 — до стабильного релиза; P2 — исправить в ближайшем цикле. «Подтверждено по коду» не означает, что проводилась эксплуатация на рабочей системе.

1. **P0. SUID-ядро доверяет имени родителя и предоставляет произвольные файловые операции.**

   Источники на проверенном commit `bc06d89`: [setup-cap.sh](https://github.com/kum1te/beaxty-vpn/blob/bc06d89/scripts/setup-cap.sh#L50), [parentcheck.go](../3rdparty/throne/core/server/parentcheck/parentcheck.go#L14), [server.go](../3rdparty/throne/core/server/server.go#L904), [dashboard_unix.go](../3rdparty/throne/core/server/dashboard_unix.go#L11).

   Скрипт выставляет `root:root` и `4755`. Проверка родителя допускает любой исполняемый файл с именем `beaxty-vpn`, `Throne` или префиксом `test_`; проверок доверенной установки/владельца родительского executable нет. Проверка IPC peer PID полезна, но здесь подтверждает лишь того же недоверенного родителя.

   Через зарегистрированный RPC `InstallDashboard` вызывающий задаёт `target_dir`. Ядро создаёт дерево, меняет владельца извлечённых файлов на пользователя, затем вызывает `os.RemoveAll(targetDir)` и заменяет этот каталог. Цель не ограничена каталогом данных приложения. На установленном SUID-ядре это даёт недоверенному локальному процессу путь к файловым операциям с правами root. Защита от `../` внутри ZIP не ограничивает сам `target_dir`.

   В `dev` путь dashboard RPC теперь фиксируется через env, заданный GUI при старте, архив ограничен базовым каталогом, shell-вызовы установки прав больше не строятся через `system()`, а при root-запуске родитель и core должны находиться в одном каталоге и принадлежать root без записи для группы/остальных. Это уменьшает поверхность, но не устраняет главную проблему универсального SUID и доверия к цепочке установки. Предлагаю убрать SUID у сетевого ядра и отделить необходимые привилегированные операции в минимальный сервис/helper с узким протоколом. `InstallDashboard` и другие ненужные приложению методы убрать из привилегированной поверхности; файловую работу выполнять от пользователя и только в разрешённых каталогах. Эксплуатация с root не запускалась.

2. **P1. Kill Switch сообщает о блокировке без гарантии её установки.**

   Источник: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L908).

   `m_killSwitchEngaged` и сообщение «весь трафик заблокирован» выставляются до проверки результата. RPC Start с блокирующим конфигом и `ip route add blackhole default metric 1` не проверяются. Команда `ip` выполняется от GUI: SUID/capabilities дочернего ядра не дают GUI права менять маршруты. Команда затрагивает IPv4 default, не весь IPv4/IPv6 трафик; более специфические маршруты остаются отдельным вопросом. На Windows/macOS независимой блокировки после смерти ядра в этой функции нет.

   Failover вызывается раньше Kill Switch и при успехе выхода из `triggerFailover()` блокировка вообще пропускается. В `doStartConnection()` блокировка снимается до подтверждения нового соединения. После падения GUI некому установить её задним числом.

   Предлагаю предварительно устанавливать правила firewall, которые сохраняют запрет при падении процессов; реализовать политики nftables/WFP/pf либо платформенный защищённый сервис. Снимать запрет только по явно определённой политике. Проверять установку и состояние правил, исключения для DNS/bootstrap/VPN endpoint, IPv4/IPv6 и переходы reconnect/failover. Проверка — реальный захват пакетов в изолированной среде.

3. **P1. HWID отправлялся в исходном виде при обычной последовательности запуска. Исправлено локально, нужны сетевые проверки.**

   Источники: [main.cpp](../src/main.cpp#L247), [DeviceIdentity.cpp](../src/core/DeviceIdentity.cpp#L21), [HTTPRequestHelper.cpp](../3rdparty/throne/src/global/HTTPRequestHelper.cpp#L146), [DeviceDetailsHelper.cpp](../3rdparty/throne/src/global/DeviceDetailsHelper.cpp#L133).

   До исправления `DeviceIdentity` конструировался до `engine.initialize()`. Базы ещё не было, поэтому запись `sub_custom_hwid_params` с SHA-256 пропускалась, а сетевой helper использовал сырой machine-id. В `dev` база и настройки инициализируются до `DeviceIdentity`, а helper хеширует fallback перед отправкой; локальный harness подтвердил, что заголовок совпадает с отображаемым хешем и не равен raw machine-id.

   Остаются отдельные задачи: ограничить отправку HWID и модели устройства доверенными HTTPS-origin, задать политику для сторонних подписок и проверить редиректы. Сейчас заголовки формируются для любой подписки при включённом флаге, включая HTTP.

4. **P1. SSRF-фильтр не соответствует заявленной политике. Основные локальные диапазоны заблокированы, DNS/redirect политика остаётся.**

   Источники: [HTTPRequestHelper.cpp](../3rdparty/throne/src/global/HTTPRequestHelper.cpp#L19), [DeepLinkManager.cpp](../src/core/DeepLinkManager.cpp#L113).

   В `dev` фильтр блокирует RFC1918, CGNAT, link-local, IPv6 ULA, multicast и dotted `localhost`; обход loopback разрешён только при явном `BEAXTY_ALLOW_LOCAL_TEST_REQUESTS=1`. Проверка hostname выполняет DNS lookup, но защита от TOCTOU/DNS rebinding и автоматических redirect остаётся незавершённой.

   Deep link открывает форму импорта, а не молча выполняет запрос — это уменьшает риск и учтено в оценке. Однако после подтверждения импорта защита остаётся неполной.

   Предлагаю единый валидатор адресов, ручную обработку редиректов, запрет userinfo, HTTPS по умолчанию, проверку всех A/AAAA и защиту от смены разрешённого адреса между проверкой и соединением. Если локальные подписки нужны — явный отдельный режим. Тестовые послабления убрать из production-политики.

5. **P1. В Linux-пакетах отключена песочница браузера; Windows GUI всегда повышен.**

   Источники: [package_linux.sh](../scripts/package_linux.sh#L215), [main.cpp](../src/main.cpp#L156), [CMakeLists.txt](../CMakeLists.txt#L338).

   До исправления AppImage/portable и main выставляли `--no-sandbox` автоматически. В `dev` этот флаг больше не включается сам: он доступен только при явном `BEAXTY_ALLOW_NO_SANDBOX=1` для диагностики. Работоспособность sandbox helper в каждом Linux-пакете всё ещё нужно проверить. [Официальная документация Qt](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html#sandboxing-support).

   До исправления Windows запускал весь GUI с `requireAdministrator`, включая обработку подписок и встроенный кабинет. В `dev` манифест переведён на `asInvoker`, а автоматический `runas` удалён. Реальный Windows-путь выдачи прав core/helper ещё нужно проверить отдельно.

   Предлагаю обычные пользовательские права для GUI, узкий привилегированный helper, работоспособную sandbox-конфигурацию. Если sandbox недоступна — системный браузер вместо её автоматического отключения. Пересмотреть использование Qt 6.8.0 в CI и политику обновления Chromium/Qt; конкретные Qt CVE в этой проверке не устанавливались.

6. **P1. Whitelist кабинета разбирает URL неправильно; внешние схемы уходят в ОС.**

   Источники: [CabinetWebEngineComponent.qml](../src/ui/qml/views/CabinetWebEngineComponent.qml#L38), [CabinetView.qml](../src/ui/qml/views/CabinetView.qml#L432), [NodesView.qml](../src/ui/qml/views/NodesView.qml#L681).

   До исправления regex брал authority, затем `split(":")[0]` считал его хостом. Например, `https://cabinet.beaxty.com:443@untrusted.example/` проходил условие whitelist, хотя сетевой host — `untrusted.example`. В `dev` QML передаёт адреса в общий C++ helper на базе строгого `QUrl`; встроенный origin ограничен точным `https://cabinet.beaxty.com` (без userinfo и нестандартного порта). Внешняя передача допускает только корректный HTTPS URL без userinfo и IP literal, и происходит после прямого клика по ссылке; автоматические redirect и popup во внешний браузер не отправляются.

   Navigation whitelist не ограничивает все subresource/WebSocket-запросы — для политики на уровне запросов нужен request interceptor. OAuth и другие потоки, которые уходят с cabinet через автоматический redirect, встраиваемая версия может блокировать; этот путь нужно отдельно проверить с владельцем сайта. Заголовки подписок тоже требуют отдельной проверки URL.

7. **P1. Потоки подключения имеют гонки и неупорядоченные Start/Stop.**

   Источники: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L648), [ThroneEngine.hpp](../src/core/ThroneEngine.hpp#L127), [RPC.cpp](../3rdparty/throne/src/api/RPC.cpp#L130), [dispatch.go](../3rdparty/throne/core/server/dispatch.go#L70).

   Ранее worker-лямбды читали обычные `m_userWantsConnect` и `m_intentionalStop`, а `ThroneEngine` продолжал читать и удалять `m_rpcSocket` после того, как Throne RPC переносил сокет в собственный I/O-поток. В `dev` состояние намерения и остановки атомарно; сырой указатель сокета удалён, Engine использует атомарный признак подключения и поколение для игнорирования запоздавшего disconnect от старого сокета. Отдельный однопоточный pool теперь сериализует Start/Stop; запоздавший UI callback больше не посылает дополнительный Stop. `cleanup()` отменяет ожидающие задачи и ждёт активную RPC-операцию, прежде чем завершить core. Это убирает гонку порядка команд и не даёт рабочим лямбдам пережить объект.

   Остался риск чтения изменяемых репозиториев во время фоновой сборки конфигурации. При максимальном 30-секундном RPC timeout завершение приложения может ждать текущий запрос; кроме того, эти изменения ещё не прошли ThreadSanitizer или стресс-тесты. Нужны immutable snapshot настроек/профиля и проверка быстрого connect/disconnect/restart/failover.

8. **P1. Failover не восстанавливает умерший демон; причина остановки теряется.**

   Источники: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L1091), [main.cpp](../src/main.cpp#L266), [MainWindowBridge.cpp](../src/bridge/MainWindowBridge.cpp#L95).

   До исправления после `onCoreExited()` выбирался другой сервер и планировался `startConnection()`, но `spawnCoreDaemon()` не вызывался. В `dev` `startConnection()` восстанавливает daemon и ждёт IPC-ready, если процесс завершился или сокет ещё не подключён. Разделение crash/tunnel failure/manual stop и backoff всё ещё нужны; bridge по-прежнему требует отдельной проверки политики Kill Switch.

   Предлагаю разделить crash/tunnel failure/manual stop, перезапускать демон с backoff и ждать IPC-ready вместо фиксированных таймеров. Ограничить число попыток и проверять фактическое восстановление.

9. **P1. Маскирование логов подписок улучшено, но диагностика всё ещё может раскрывать данные.**

   Источники: [DeepLinkManager.cpp](../src/core/DeepLinkManager.cpp#L146), [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L373), [tests/test_security_audit.cpp](../tests/test_security_audit.cpp#L163).

   В `dev` deep link и HTTP helper записывают только scheme/host/port, а не path/query/fragment с токеном. При `THRONE_CORE_DEBUG=1` ядро всё ещё может логировать полные конфиги. Отчёт также содержит hostname, MAC/сетевые данные и DNS окружения.

   Нужно централизовать redaction для всех Qt/core логов, отключить полные конфиги в production-debug режиме, документировать состав отчёта и проверить права файла. Отдельно подключить нормальную инициализацию Logger: в main нет вызовов `Logging::Init`/`InstallQtMessageHandler`, поэтому recent Qt/core logs могут отсутствовать в отчёте.

10. **P1 перед публикацией. В исходниках и истории присутствует похожая на реальную bearer-ссылка подписки.**

    Источник: [ConfigAdapter.cpp](../src/core/ConfigAdapter.cpp#L233), история `tests/test_subscription_import.cpp`.

16. **P2. IPC ограничивает кадры, но требует единственного соединения и лимитов параллелизма.**

    Источники: [dispatch.go](../3rdparty/throne/core/server/dispatch.go#L60), [RPC.cpp](../3rdparty/throne/src/api/RPC.cpp#L57), [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L549).

    В `dev` Go отклоняет method/payload больше 256/16 MiB, ставит 30-секундный read deadline и больше не завершает весь core при обрыве IPC; C++ отклоняет ответы больше 16 MiB. На Linux GUI до передачи сокета RPC проверяет через `SO_PEERCRED`, что peer имеет UID текущего пользователя и PID именно запущенного дочернего core; проверка credentials вынесена в helper и покрыта безопасным `socketpair`-тестом. На Windows/macOS отдельной проверки PID нет; там core не получает Linux `CAP_NET_ADMIN`. Число параллельных запросов всё ещё не ограничено, и GUI не сверяет себя с сервером со стороны core.

    Следующие шаги: проверить одно активное соединение, добавить лимиты in-flight/backpressure и fuzz-тесты malformed frames. Для взаимной аутентификации нужен протокольный handshake либо проверка peer credentials в core.

17. **P2. Тесты создают избыточную уверенность в безопасности.**

    Источники: [test_security_audit.cpp](../tests/test_security_audit.cpp#L25), [test_security_audit.sh](../tests/test_security_audit.sh#L40), [CMakeLists.txt](../CMakeLists.txt#L406).

    Redaction-тест повторяет regex вместо вызова функции продукта. SSRF-тесты не проверяют RFC1918/ULA/DNS/redirect. IPv6-тест подтверждает наличие JSON reject, а не поведение сетевого стека. Shell audit считает наличие слов cap_net_admin достаточной проверкой привилегий; после нахождения утечки выставляет LEAK_FOUND, но не завершает проверку ошибкой, и запуск приложения допускает `|| true`.

    После аудита удалены старые ручные performance/TUN/ping-пробы: они запускали реальный бинарник, писали в фиксированные `/tmp` или пользовательскую БД, а TUN-скрипт мог завершать посторонние процессы по имени. CTest заменён безопасными сценариями с уникальными `QTemporaryDir` и явно отсутствующим core; добавлена статическая проверка, запрещающая автообнаружение core в тестах. UI screenshot harness тоже не загружает живой кабинет. Это не покрывает производственный connect/disconnect, IPC-подмену, TUN, DNS/IPv6 утечки и crash-recovery; текущие security assertions всё ещё местами повторяют ожидаемую структуру, а не проверяют production-путь.

    Дальше нужны тесты production-политик без привилегий, ASan/TSan, mock IPC daemon и отдельный изолированный интеграционный стенд сетевых утечек. Не запускать TUN-тесты на машине разработчика или CI runner с пользовательской сетью.

**Что уже сделано правильно и стоит сохранить**

- Разделение GUI/ядра и private user-access IPC socket.
- Проверка PID родителя со стороны ядра, хотя её доверительная модель требует исправления.

## Дополнение: повторная проверка текущего рабочего дерева `dev`

Проверка выполнена 26 сентября 2026 после предыдущих исправлений. Ниже отмечены только новые результаты и актуальные ограничения; пункты выше описывают исходный аудит и остаются историей найденных проблем, если здесь явно не сказано, что они закрыты. Изменения в этом дополнении находятся в локальном рабочем дереве и не отправлены в GitHub.

**Что проверено и исправлено в этой итерации**

1. **Локальный канал активации и системные deep links.** Раньше блокировка и сокет имели фиксированные имена в общем `/tmp`/пространстве локальных сокетов. Сервер не ограничивал доступ по UID, читал весь буфер без лимита и принимал произвольную строку как deep link. Теперь канал расположен в per-user runtime-каталоге с режимом `0700`, сокет ограничен `UserAccessOption`, Linux/macOS проверяют UID peer, запрос ограничен 8 KiB, одной командой и таймаутом 2 секунды. Некорректный UTF-8, дополнительные строки, NUL и oversized payload отбрасываются. Системные deep links также ограничены 8 KiB и разбираются `QUrl::StrictMode`; вложенные subscription URL с user-info отклоняются. Реальный сетевой core для проверки не запускался. См. [ActivationChannel.cpp](../src/core/ActivationChannel.cpp), [DeepLinkManager.cpp](../src/core/DeepLinkManager.cpp) и [main.cpp](../src/main.cpp).

2. **Передача device ID подписочным серверам.** По умолчанию настройки Throne могут включать HWID. В `HttpGetAsync` идентификатор и сведения об устройстве теперь добавляются только к HTTPS-запросу с включённой проверкой TLS; для такого запроса разрешён redirect только в тот же origin. URL с user-info вида `user:pass@host` блокируется. Локальный HTTP regression-тест подтвердил отсутствие заголовка `x-hwid`. Это не отменяет риск раскрытия токена подписки в URL при использовании HTTP: сам HTTP-запрос по-прежнему допустим, но без device headers. HWID — стабильный псевдоним, а не анонимизация: по умолчанию серверы подписок могут сопоставлять его с OS/model и связывать запросы между собой; пользователь должен понимать это и иметь доступный переключатель.

3. **Файл диагностического отчёта.** Отчёт содержит hostname, таблицы маршрутизации и DNS-данные. Он сохраняется атомарно через `QSaveFile`; на Unix временный файл получает права только владельца до записи содержимого. Состав отчёта всё равно нужно считать чувствительным и передавать только после просмотра.

4. **Публикация релиза в GitHub Actions.** Ручной `release_tag` передаётся через environment, валидируется и должен совпасть с выбранным tag ref. Проверяющая job фиксирует commit SHA; все платформы собирают именно его, а publish job сверяет, что тег не передвинулся во время сборки. Артефакты трёх платформ собираются до публикации; только отдельный publish job получает `contents:write`, создаёт draft, загружает файлы без `--clobber` и снимает draft после успешной загрузки. Уже опубликованный release не перезаписывается. Остался supply-chain риск: сторонние Actions и часть инструментов ещё не закреплены по commit SHA/проверенному digest.

**Оставшиеся приоритетные риски**

- **P1 — Linux `CAP_NET_ADMIN` и авторизация запуска ядра.** Ядро остаётся отдельным root-owned файлом с узкой `CAP_NET_ADMIN`, что предотвращает выдачу ему SUID-root. Однако `validatePrivilegedParent()` сразу пропускает проверки, когда effective UID не равен 0 — это обычный режим file capabilities. Общая проверка родителя затем смотрит только basename (`beaxty-vpn`/`Throne`/`test_*`). Поэтому процесс того же UID, который способен запустить копию-launcher с разрешённым именем, может запустить capability-bearing core вне штатного GUI. Это локальная граница полномочий, а не доказанный удалённый root-RCE; она позволяет злоупотреблять сетевыми возможностями core. Нужна архитектура, где privileged endpoint авторизует только доверенную установленную GUI/сессию и принимает ограниченные операции. До решения этого вопроса не следует обещать защиту от вредоносной программы, уже запущенной под аккаунтом пользователя.
- **P1 — Kill Switch не системный.** Он не гарантирует блокировку после падения GUI/core, выхода из приложения или ошибок настройки маршрута. Нужны платформенные правила firewall и испытание в изолированной VM с IPv4/IPv6, DNS, suspend, reconnect и аварийным завершением. Такие тесты не проводились.
- **P1 — DNS rebinding/SSRF.** Хост подписки сначала проверяется отдельным DNS lookup, а Qt затем самостоятельно разрешает его при подключении. Между проверкой и соединением ответ может измениться; автоматические redirects для запросов без device headers остаются. Полной защиты от SSRF только текущим URL-фильтром нет.
- **P1 — HTTP, недоверенный TLS и содержимое подписок.** Публичные HTTP URL всё ещё разрешены, а настройка `net_insecure` может отключить проверку сертификата. Токен в URL, сетевой конфиг и узлы подписки в этих режимах доступны сетевому наблюдателю или MITM. Нужны HTTPS по умолчанию, ясное подтверждение исключения и политика редиректов с тестами на DNS/IPv4/IPv6.
- **P2 — хранение секретов.** Основная SQLite база ограничена правами Unix `0600`, что защищает её от других обычных аккаунтов, но профили содержат конфигурационные credentials в читаемом виде. Копия базы/резервной копии или компрометация того же аккаунта открывает их; шифрования через системный keyring нет. Это ограничение нужно явно описать и оценить перед добавлением шифрования, чтобы не потерять совместимость и восстановление данных.
- **P1 — поставка и CI.** Установочные инструменты/Actions и Wintun не все закреплены проверенными digest/commit; отдельный CI на PR с полным тестовым набором ещё нужен. Нужны SBOM, закреплённые версии и подпись/проверка опубликованных артефактов.
- **P2 — встроенный кабинет.** Ограничение навигации верхнего уровня не ограничивает сетевые подресурсы страницы. Для уменьшения риска CSRF к localhost/LAN и последствий XSS нужна проверка запросов WebEngine через interceptor; DNS-имя само по себе не доказывает, что соединение не уйдёт на локальный адрес.
- **Платформы и сторонний код.** В этой среде проверена сборка Linux. Windows/macOS, фактический TUN, системные firewall-правила, QtWebEngine sandbox в собранном AppImage и сетевой failover не запускались. Go security audit из предыдущей части относится к версиям модулей и потенциальным call paths, а не к доказанной эксплуатации; форки Throne требуют собственного обновления и проверки.

В изученных deep link, IPC, импорте подписки и helper-коде **прямой воспроизводимой удалённой цепочки до RCE не обнаружено**. Это не доказывает отсутствие RCE в полном проекте: исходники Throne, форки sing-box/Xray, Go-модули, Chromium/Qt WebEngine и драйверы слишком велики для заявления о полной построчной сертификации. Главная практическая блокировка распространения остаётся в локальной границе `CAP_NET_ADMIN` и отсутствии гарантированного системного Kill Switch.

**Проверка этой итерации:** Linux цели `beaxty-vpn`, `test_activation_channel`, `test_core_peer_auth`, `test_security_audit` и `test_subscription_safety` собрались; CTest прошёл 14/14; `tests/test_security_audit.sh` прошёл. Network regression использовал локальный loopback mock и временную базу. Живой Throne, GUI пользователя, настоящий tunnel и внешняя инфраструктура сервиса не запускались.
