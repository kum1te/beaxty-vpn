# Проверка BeaxtyVPN — 26 сентября 2026

Проверен commit `bc06d89` (`main`, `origin/main`). На момент начала проверки `docs/` не отслеживался Git. Исходный аудит не менял сетевые настройки ОС; перечисленные ниже исправления были внесены после проверки в `dev` и отдельно проверены.

После аудита в `dev` уже исправлены локальные дефекты: HWID больше не отправляется сырым machine-id, URL-фильтр блокирует RFC1918/ULA и dotted localhost, встроенный кабинет корректно разбирает userinfo и отклоняет HTTP-auth dialogs, `--tray` зарегистрирован и скрывает окно, ссылки подписок маскируются в логах, а privileged dashboard RPC ограничен путями, переданными при запуске. Shell-вызовы `pkexec` переведены на аргументы без `system()`, а SUID-ядро теперь дополнительно проверяет владельца и права родителя и самого executable. P0-проблема универсального SUID/helper, Kill Switch и lifecycle подключения пока не исправлены.

**Вывод:** текущую сборку нельзя считать готовой к релизу с обещанием защиты данных и надёжного Kill Switch. Есть критическая проблема границы привилегий, воспроизведённая утечка исходного идентификатора устройства и несколько ошибок защитных механизмов. Открытие исходников и выпуск стабильного приложения — разные этапы: перед первым необходимо проверить историю и реальные учётные данные, перед вторым — закрыть дефекты ниже.

**Объём и ограничения**

Изучены карта проекта, CMake, release workflow, основной C++/QML слой, запуск и остановка ядра, IPC/проверка родителя, сетевой helper, импорт подписок, генератор маршрутизации, хранение, диагностический отчёт и существующие тесты. При спорном выводе по IPv6 дополнительно изучен установленный исходник sing-tun v0.9.0-beta.4.

Это углублённое ревью основных путей исполнения с локальными проверками. Оно не является построчной сертификацией всех сторонних библиотек. Реальный VPN-трафик, обрыв туннеля, Windows/macOS, веб-страница кабинета и эксплуатация от root не испытывались. Рабочие подписки сервиса не запрашивались.

1. **P0. SUID-ядро доверяет имени родителя и предоставляет произвольные файловые операции.**

   Источники: [setup-cap.sh](../scripts/setup-cap.sh#L50), [parentcheck.go](../3rdparty/throne/core/server/parentcheck/parentcheck.go#L14), [server.go](../3rdparty/throne/core/server/server.go#L904), [dashboard_unix.go](../3rdparty/throne/core/server/dashboard_unix.go#L11).

   Скрипт выставляет `root:root` и `4755`. Проверка родителя допускает любой исполняемый файл с именем `beaxty-vpn`, `Throne` или префиксом `test_`; проверок доверенной установки/владельца родительского executable нет. Проверка IPC peer PID полезна, но здесь подтверждает лишь того же недоверенного родителя.

   Через зарегистрированный RPC `InstallDashboard` вызывающий задаёт `target_dir`. Ядро создаёт дерево, меняет владельца извлечённых файлов на пользователя, затем вызывает `os.RemoveAll(targetDir)` и заменяет этот каталог. Цель не ограничена каталогом данных приложения. На установленном SUID-ядре это даёт недоверенному локальному процессу путь к файловым операциям с правами root. Защита от `../` внутри ZIP не ограничивает сам `target_dir`.

   В `dev` путь dashboard RPC теперь фиксируется через env, заданный GUI при старте, архив ограничен базовым каталогом, shell-вызовы установки прав больше не строятся через `system()`, а при root-запуске родитель и core должны находиться в одном каталоге и принадлежать root без записи для группы/остальных. Это уменьшает поверхность, но не устраняет главную проблему универсального SUID и доверия к цепочке установки. Предлагаю убрать SUID у сетевого ядра и отделить необходимые привилегированные операции в минимальный сервис/helper с узким протоколом. `InstallDashboard` и другие ненужные приложению методы убрать из привилегированной поверхности; файловую работу выполнять от пользователя и только в разрешённых каталогах. Эксплуатация с root не запускалась.

2. **P1. Kill Switch сообщает о блокировке без гарантии её установки.**

   Источник: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L908).

   `m_killSwitchEngaged` и сообщение «весь трафик заблокирован» выставляются до проверки результата. RPC Start с блокирующим конфигом и `ip route add blackhole default metric 1` не проверяются. Команда `ip` выполняется от GUI: SUID/capabilities дочернего ядра не дают GUI права менять маршруты. Команда затрагивает IPv4 default, не весь IPv4/IPv6 трафик; более специфические маршруты остаются отдельным вопросом. На Windows/macOS независимой блокировки после смерти ядра в этой функции нет.

   Failover вызывается раньше Kill Switch и при успехе выхода из `triggerFailover()` блокировка вообще пропускается. В `doStartConnection()` блокировка снимается до подтверждения нового соединения. После падения GUI некому установить её задним числом.

   Предлагаю предварительно устанавливать правила firewall, которые сохраняют запрет при падении процессов; реализовать политики nftables/WFP/pf либо платформенный защищённый сервис. Снимать запрет только по явно определённой политике. Проверять установку и состояние правил, исключения для DNS/bootstrap/VPN endpoint, IPv4/IPv6 и переходы reconnect/failover. Проверка — реальный захват пакетов в изолированной среде.

3. **P1. HWID отправлялся в исходном виде при обычной последовательности запуска. Исправлено локально, нужны сетевые проверки.**

   Источники: [main.cpp](../src/main.cpp#L247), [DeviceIdentity.cpp](../src/core/DeviceIdentity.cpp#L21), [HTTPRequestHelper.cpp](../3rdparty/throne/src/global/HTTPRequestHelper.cpp#L146), [DeviceDetailsHelper.cpp](../3rdparty/throne/src/global/DeviceDetailsHelper.cpp#L133).

   До исправления `DeviceIdentity` конструировался до `engine.initialize()`. Базы ещё не было, поэтому запись `sub_custom_hwid_params` с SHA-256 пропускалась, а сетевой helper использовал сырой machine-id. В `dev` база и настройки инициализируются до `DeviceIdentity`, а helper хеширует fallback перед отправкой; локальный harness подтвердил, что заголовок совпадает с отображаемым хешем и не равен raw machine-id.

   Остаются отдельные задачи: ограничить отправку HWID и модели устройства доверенными HTTPS-origin, задать политику для сторонних подписок и проверить редиректы. Сейчас заголовки формируются для любой подписки при включённом флаге, включая HTTP.

4. **P1. SSRF-фильтр не соответствует заявленной политике. Основные локальные диапазоны заблокированы, DNS/redirect политика остаётся.**

   Источники: [HTTPRequestHelper.cpp](../3rdparty/throne/src/global/HTTPRequestHelper.cpp#L19), [DeepLinkManager.cpp](../src/core/DeepLinkManager.cpp#L113).

   В `dev` фильтр блокирует RFC1918, CGNAT, link-local, IPv6 ULA, multicast и dotted `localhost`; обход loopback разрешён только при явном `BEAXTY_ALLOW_LOCAL_TEST_REQUESTS=1`. Проверка hostname выполняет DNS lookup, но защита от TOCTOU/DNS rebinding и автоматических redirect остаётся незавершённой.

   Deep link открывает форму импорта, а не молча выполняет запрос — это уменьшает риск и учтено в оценке. Однако после подтверждения импорта защита остаётся неполной.

   Предлагаю единый валидатор адресов, ручную обработку редиректов, запрет userinfo, HTTPS по умолчанию, проверку всех A/AAAA и защиту от смены разрешённого адреса между проверкой и соединением. Если локальные подписки нужны — явный отдельный режим. Тестовые послабления убрать из production-политики.

5. **P1. В Linux-пакетах отключена песочница браузера; Windows GUI всегда повышен.**

   Источники: [package_linux.sh](../scripts/package_linux.sh#L215), [main.cpp](../src/main.cpp#L156), [CMakeLists.txt](../CMakeLists.txt#L338).

   До исправления AppImage/portable и main выставляли `--no-sandbox` автоматически. В `dev` этот флаг больше не включается сам: он доступен только при явном `BEAXTY_ALLOW_NO_SANDBOX=1` для диагностики. Работоспособность sandbox helper в каждом Linux-пакете всё ещё нужно проверить. [Официальная документация Qt](https://doc.qt.io/qt-6/qtwebengine-platform-notes.html#sandboxing-support).

   До исправления Windows запускал весь GUI с `requireAdministrator`, включая обработку подписок и встроенный кабинет. В `dev` манифест переведён на `asInvoker`, а автоматический `runas` удалён. Реальный Windows-путь выдачи прав core/helper ещё нужно проверить отдельно.

   Предлагаю обычные пользовательские права для GUI, узкий привилегированный helper, работоспособную sandbox-конфигурацию. Если sandbox недоступна — системный браузер вместо её автоматического отключения. Пересмотреть использование Qt 6.8.0 в CI и политику обновления Chromium/Qt; конкретные Qt CVE в этой проверке не устанавливались.

6. **P1. Whitelist кабинета разбирает URL неправильно; внешние схемы уходят в ОС.**

   Источники: [CabinetWebEngineComponent.qml](../src/ui/qml/views/CabinetWebEngineComponent.qml#L38), [CabinetView.qml](../src/ui/qml/views/CabinetView.qml#L432), [NodesView.qml](../src/ui/qml/views/NodesView.qml#L681).

   До исправления regex брал authority, затем `split(":")[0]` считал его хостом. Например, `https://cabinet.beaxty.com:443@untrusted.example/` проходил условие whitelist, хотя сетевой host — `untrusted.example`. В `dev` разбор выполняется через `QUrl`, userinfo удаляется из доверенного сравнения, а внешние ссылки ограничены `http/https`. Subresource/WebSocket-политика по-прежнему требует request interceptor.

   В `dev` отклонённые URL передаются наружу только при схеме `http/https`; userinfo не используется в доверенном сравнении. Требование пользовательского жеста и проверка URL из заголовков подписки остаются отдельными задачами.

   Предлагаю разбор `QUrl` в C++, сравнение точного origin (scheme/host/port), запрет userinfo, отдельную allowlist внешних схем и явный пользовательский жест. Navigation whitelist не ограничивает все subresource/WebSocket-запросы — для такой политики нужен request interceptor.

7. **P1. Потоки подключения имеют гонки и неупорядоченные Start/Stop.**

   Источники: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L648), [ThroneEngine.hpp](../src/core/ThroneEngine.hpp#L127), [RPC.cpp](../3rdparty/throne/src/api/RPC.cpp#L130), [dispatch.go](../3rdparty/throne/core/server/dispatch.go#L70).

   Worker-лямбды захватывают сырой `this`, читают обычные `m_userWantsConnect`, `m_intentionalStop`, `m_rpcSocket` параллельно их изменению GUI. Атомарен только sequence counter. Сокет перемещается в IPC-поток, но его состояние читается и закрывается из других потоков. `cleanup()` не дожидается всех задач, захвативших engine.

   `stopConnection()` отправляет Stop через общий thread pool без привязки к поколению. Старый Stop или компенсационный Stop отменённого Start может остановить более новое подключение. Go запускает запросы в отдельных goroutine; lifecycle mutex предотвращает одновременное исполнение, но не гарантирует нужный порядок поколений GUI.

   Предлагаю один последовательный controller жизненного цикла, immutable snapshot настроек, отменяемые операции с generation ID, строгое владение QObject и завершение задач перед уничтожением. Подтверждено по коду; ThreadSanitizer и стресс-тест переключений ещё нужны.

8. **P1. Failover не восстанавливает умерший демон; причина остановки теряется.**

   Источники: [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L1091), [main.cpp](../src/main.cpp#L266), [MainWindowBridge.cpp](../src/bridge/MainWindowBridge.cpp#L95).

   До исправления после `onCoreExited()` выбирался другой сервер и планировался `startConnection()`, но `spawnCoreDaemon()` не вызывался. В `dev` `startConnection()` восстанавливает daemon и ждёт IPC-ready, если процесс завершился или сокет ещё не подключён. Разделение crash/tunnel failure/manual stop и backoff всё ещё нужны; bridge по-прежнему требует отдельной проверки политики Kill Switch.

   Предлагаю разделить crash/tunnel failure/manual stop, перезапускать демон с backoff и ждать IPC-ready вместо фиксированных таймеров. Ограничить число попыток и проверять фактическое восстановление.

9. **P1. Маскирование логов подписок улучшено, но диагностика всё ещё может раскрывать данные.**

   Источники: [DeepLinkManager.cpp](../src/core/DeepLinkManager.cpp#L146), [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L373), [tests/test_security_audit.cpp](../tests/test_security_audit.cpp#L163).

   В `dev` deep link и HTTP helper записывают только scheme/host/port, а не path/query/fragment с токеном. При `THRONE_CORE_DEBUG=1` ядро всё ещё может логировать полные конфиги. Отчёт также содержит hostname, MAC/сетевые данные и DNS окружения.

   Нужно централизовать redaction для всех Qt/core логов, отключить полные конфиги в production-debug режиме, документировать состав отчёта и проверить права файла. Отдельно подключить нормальную инициализацию Logger: в main нет вызовов `Logging::Init`/`InstallQtMessageHandler`, поэтому recent Qt/core logs могут отсутствовать в отчёте.

10. **P1 перед публикацией. В исходниках и истории присутствует похожая на реальную bearer-ссылка подписки.**

    Источник: [ConfigAdapter.cpp](../src/core/ConfigAdapter.cpp#L233), история `tests/test_subscription_import.cpp`.

    URL не воспроизвожу в отчёте. Он находится в demo-данных, но это не делает его безопасным для публикации. Проверка действительности не проводилась. В тестах также есть реалистичные VLESS-реквизиты; происхождение следует проверить. Демо-пароль с очевидным тестовым именем не считаю автоматически подтверждённым действующим секретом.

    Предлагаю заменить fixture-данные доменами `example.invalid` и искусственными реквизитами. Если ссылка/UUID действующие — сначала отозвать/сменить их. Затем проверить все refs, теги, артефакты и доступную удалённую историю полноценным secret scanner. Удаление строки из текущего файла не удаляет её из Git history; массовое переписывание истории выполнять отдельно и осознанно.

11. **P1. Release CI публикует результат до завершения проверок и может смешать tag с другим исходным кодом.**

    Источник: [.github/workflows/build-release.yml](../.github/workflows/build-release.yml#L18).

    Сначала создаётся обычный release; платформы загружают файлы независимо с `--clobber`. При падении одной платформы уже опубликован неполный release. Нет workflow на pull_request/push dev и нет запуска CTest/Go tests в релизном workflow; Linux smoke лишь запускает окно на две секунды.

    Предлагаю отдельные CI и release workflows, обязательные проверки PR, сборку всех платформ из одного проверенного commit/tag, draft до успеха всех jobs, контроль SHA и запрет перезаписи опубликованных артефактов. Дать contents:write только job публикации, передавать input через env, закрепить сторонние actions по commit SHA.

Дополнительный анализ корневого Linux-пакета с release build tags (`govulncheck -tags=... -format=json .`) нашёл потенциальные call paths для 5 advisory IDs: GO-2026-6303, GO-2026-6348, GO-2026-6354, GO-2026-6355, GO-2026-6443. Это усиливает приоритет обновления x/crypto и grpc, но статический граф вызовов, особенно через интерфейсы io.Reader/io.Writer, может переоценивать фактическую достижимость. Эксплуатация не воспроизводилась. В расширенном графе также найдено module-level совпадение GO-2026-6237 для github.com/insomniacslk/dhcp (DoS на повреждённом IPv4-пакете); вызов затронутой функции не отмечен. База vuln.go.dev обновлена 2026-09-24. Сырые локальные результаты: `/tmp/beaxty-review/govulncheck.json` и `/tmp/beaxty-review/govulncheck-linux.json`.

    sing-box/Xray фактически подменены через `replace` на форки Throne; заявленный version string не описывает весь используемый код. Плагины protobuf ставятся через `@latest`, Go в CI — `stable`, linuxdeploy/appimagetool скачиваются из `continuous`, Wintun скачивается без проверки известного digest. Это мешает воспроизводимости и контролю цепочки поставки.

    Предлагаю закрепить версии и digest инструментов, составлять SBOM с реальными replace-commit, проверять advisories в CI, обновлять зависимости отдельными PR с тестами. Не заменять форки на upstream вслепую.

13. **P1 для macOS-релиза. Имя GUI не проходит проверку родителя ядра; Universal не собирается.**

    Источники: [CMakeLists.txt](../CMakeLists.txt#L324), [parentcheck.go](../3rdparty/throne/core/server/parentcheck/parentcheck.go#L36), macOS job release workflow.

    CMake задаёт `OUTPUT_NAME BeaxtyVPN`, тогда как Unix parent check разрешает `Throne`, `beaxty-vpn`, `test_*`. Для штатного bundle это несовпадение приводит к отказу ядра ещё до IPC. В macOS-ветке повышения прав написано, что они обрабатываются нативно, но реализация нужного helper в пути этого приложения отсутствует.

    DMG назван Universal, но сборки обеих архитектур/`lipo` нет. Нет `CFBundleURLSchemes`/собственного Info.plist для beaxty deep links; macOS autostart в facade возвращает false.

    Предлагаю согласовать платформенный запуск с новой моделью привилегий, реально собирать arm64/x86_64 либо корректно назвать артефакты; реализовать URL registration и отдельно обозначить поддержку автозапуска. Подтверждено по сборочным файлам, на macOS не запускалось.

14. **P2. Автозапуск с `--tray` исправлен локально; нужны проверки установочных шаблонов.**

    Источники: [AutostartManager.cpp](../src/core/AutostartManager.cpp#L77), [main.cpp](../src/main.cpp#L185).

   До исправления Linux desktop и Windows Run использовали `-tray`, но QCommandLineParser его не регистрировал. В `dev` зарегистрирован `--tray`, окно скрывается после загрузки QML, а smoke-проверка проходит без ошибки парсера. Следует проверить, что все установочные шаблоны используют одинаковое имя параметра.

15. **P2. Часть настроек читается до базы, а список приложений реализован только для Linux.**

    Источники: [AppPrefs.cpp](../src/core/AppPrefs.cpp#L114), [main.cpp](../src/main.cpp#L247), [RoutingManager.cpp](../src/core/RoutingManager.cpp#L219).

    `AppPrefsService` считывает sidebarCollapsed до открытия БД и не перечитывает его после initialize, поэтому сохранённое значение теряется в UI следующего запуска. У ConfigAdapter аналогичная проблема уже решена отдельной загрузкой prefs, но общего порядка инициализации нет.

    Список приложений читает XDG desktop files и `/proc`. Windows backend списка отсутствует, а `Q_OS_UNIX` включает macOS, где `/proc` обычно отсутствует. Blacklist по substring, в частности `sh` и `server`, даёт ложные исключения. Сканирование и сортировка выполняются синхронно.

    Предлагаю явные стадии bootstrap → DB → preferences → services → UI, платформенные providers списка процессов, кеш с фоновым обновлением и фильтрацию по точным критериям.

16. **P2. IPC ограничивает кадры, но всё ещё требует peer-аутентификации и лимита параллелизма.**

    Источники: [dispatch.go](../3rdparty/throne/core/server/dispatch.go#L60), [RPC.cpp](../3rdparty/throne/src/api/RPC.cpp#L57), [ThroneEngine.cpp](../src/core/ThroneEngine.cpp#L549).

    В `dev` Go отклоняет method/payload больше 256/16 MiB, ставит 30-секундный read deadline и больше не завершает весь core при обрыве IPC; C++ отклоняет ответы больше 16 MiB. GUI принимает новые соединения как ядро без сверки PID ожидаемого child, а число параллельных запросов не ограничено. UserAccessOption ограничивает доступ пользователем, но не аутентифицирует конкретный daemon. После исправления SUID это остаётся проблемой локальной надёжности и подмены состояния.

    Предлагаю handshake/проверку peer credentials в обоих направлениях, единственное соединение, лимиты frame/in-flight, deadline, backpressure и fuzz-тесты malformed frames.

17. **P2. Тесты создают избыточную уверенность в безопасности.**

    Источники: [test_security_audit.cpp](../tests/test_security_audit.cpp#L25), [test_security_audit.sh](../tests/test_security_audit.sh#L40), [CMakeLists.txt](../CMakeLists.txt#L406).

    Redaction-тест повторяет regex вместо вызова функции продукта. SSRF-тесты не проверяют RFC1918/ULA/DNS/redirect. IPv6-тест подтверждает наличие JSON reject, а не поведение сетевого стека. Shell audit считает наличие слов cap_net_admin достаточной проверкой привилегий; после нахождения утечки выставляет LEAK_FOUND, но не завершает проверку ошибкой, и запуск приложения допускает `|| true`.

    Часть тестов использует фиксированные `/tmp/*.db`, несколько main DB в одной директории получают общий `throne_stats.db`. Тесты responsiveness/traffic lifecycle собираются, но не зарегистрированы в основном CTest-наборе. Наличие зелёного CTest не покрывает эти пробелы.

    Предлагаю тестировать production-пути и вредоносные входы; выделить уникальные temp dirs, включить полезные lifecycle-тесты в CI, добавить ASan/TSan и интеграционный стенд сетевых утечек.

18. **P2. Документация и подготовка открытого репозитория расходятся с реализацией.**

    README ссылается на корневой LICENSE, которого нет; GPL-текст есть внутри `3rdparty/throne`. PROJECT_MAP описывает capability-only запуск вместо SUID, Go 1.22+ вместо `go 1.26`, gRPC вместо используемого framed Protobuf IPC, Universal вместо одной архитектуры. `3rdparty/throne` отслеживается как обычное дерево, а не зарегистрированный git submodule.

    Предлагаю добавить корневой LICENSE, сведения об upstream/изменениях, THIRD_PARTY_NOTICES, описание privacy/HWID, SECURITY.md и правила contribution. Проверить состав лицензий распространяемых бинарных компонентов и соответствующие исходники. Публикация исходников сама по себе не подтверждает безопасность приложения.

**Что уже сделано правильно и стоит сохранить**

- Разделение GUI/ядра и private user-access IPC socket.
- Проверка PID родителя со стороны ядра, хотя её доверительная модель требует исправления.
- Ограничение subscription response до 16 MiB, read buffer и общий deadline.
- Асинхронная загрузка подписок, coalescing обновлений ping, защита от повторного refresh.
- Обновление подписки сохраняет рабочие профили при ошибках загрузки/записи; есть полезный тест отказа SQLite.
- Параметризованные SQL-запросы и mode 0600 для основных/статистических SQLite-файлов на Unix.
- Сброс привилегий для дополнительных subprocess на Unix уже реализован; утверждать, что каждый extra process автоматически запускается root, было бы неверно.
- На Linux и Windows sing-tun реализует блокировку неподдерживаемого IP family через strict_route. Поэтому отсутствие IPv6-адреса TUN само по себе не доказывает утечку. Нужен системный тест, особенно при остановке/краше; [описание strict_route](https://sing-box.sagernet.org/configuration/inbound/tun/#strict_route).
- QtWebEngine загружается лениво и выгружается по неактивности.

**Предлагаемый порядок работы**

1. Зафиксировать исходную точку и создать `dev` от текущего commit; рабочие исправления вести через короткие ветки/PR в dev.
2. Закрыть P0 границу привилегий и убрать небезопасные privileged RPC. Одновременно исправить HWID, URL-политику и секреты в логах/fixtures.
3. Реализовать системный Kill Switch и последовательный lifecycle с корректным failover. Затем испытать IPv4/IPv6/DNS на connect/disconnect/crash/reconnect/failover/suspend/network change.
4. Исправить браузерную изоляцию, платформенные баги, автозапуск и инициализацию настроек. Обновить зависимости после проверки совместимости.
5. Подключить обязательные CI-проверки, тесты пакетированных сборок всех платформ, SBOM/digests и безопасную публикацию draft release.
6. Оптимизировать по измерениям: idle CPU/RSS с кабинетом и без, startup time, UI latency на больших подписках, фоновые списки процессов, shutdown latency. Парсинг 16 MiB подписки и запись профилей всё ещё выполняются в UI callback; их следует измерить и при необходимости перенести на worker с транзакционным применением результата. Уменьшать surface/число protocol modules только после определения реально поддерживаемых сервисом протоколов.
7. Проверить историю/артефакты на секреты, отозвать реальные реквизиты, подготовить лицензионные документы и README, затем открывать репозиторий.

**Схема dev/main для следующего этапа**

- Локально `dev` хранит полный проект и исправления, а `main` заменена предупреждающим README. Push на GitHub не выполнен из-за отсутствия GitHub-аутентификации в окружении.
- Прежний код сохранён в истории `dev`; локальная очистка `main` не удаляет его из Git history.
- До готовности первого проверенного релиза пометить проект как development/experimental. Можно сделать dev default branch, если нужно направлять туда новых участников.
- Ограничить прямые push в main, требовать PR/проверки, выпускать v-теги только с проверенной main; dev не должен автоматически обновлять stable release.
- Default branch, rulesets и visibility GitHub ещё не проверялись и не менялись.
